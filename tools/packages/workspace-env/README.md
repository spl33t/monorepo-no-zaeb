# @tools/workspace-env

Bootstrap для `.env`/`env.ts` в монорепе: перед запуском команды находит все
`.env`/`env.ts` у app'а и его `@packages/*`-зависимостей (транзитивно),
проверяет схему, инжектит значения в `process.env` и только потом запускает
переданную команду.

## Контракт `.env` / `env.ts`

Схема переменных (`env.ts`) всегда лежит рядом с `.env`, в той же директории:

```ts
// packages/database/env.ts
import { defineEnv } from '@tools/workspace-env';

export default defineEnv((z) => ({
  POSTGRES_HOST: z.string(),
  POSTGRES_PORT: z.coerce.number(),
}));
```

| Есть `.env` | Есть `env.ts` | Результат                                          |
| ----------- | -------------- | --------------------------------------------------- |
| ❌          | ❌             | пакет не участвует в workspace-env, пропуск          |
| ❌          | ✅             | OK — значения ожидаются из реального `process.env` (Docker/оркестратор) |
| ✅          | ❌             | ошибка — непровалидированные значения без схемы недопустимы |
| ✅          | ✅             | OK, обычный случай                                   |

Имя файла — `env.ts`, а не `.env.ts`: голый импорт `./.env` в webpack
резолвится сначала на реальный `.env`, точное совпадение имени побеждает
раньше, чем резолвер попробует `.ts`.

Одинаковое имя переменной в `.env` двух разных пакетов — ошибка. Никакого
авто-namespace/префикса нет, коллизию нужно решать руками (переименовать
переменную).

## Что делает `bin/workspace-env.js`

### Один цикл (`runCycle`)

Выполняется один раз при обычном запуске и заново — целиком, с нуля — при
каждом рестарте в `--watch`:

1. **Обход зависимостей.** От `appRoot` (текущая рабочая директория — `cwd`
   вызывающего app'а) рекурсивно обходит `node_modules/@packages`: сначала
   свои прямые `@packages/*`-зависимости, потом — их собственные
   `node_modules/@packages` (транзитивные зависимости пакетов друг от друга).
   Каждый физический пакет (по `realpath`) обрабатывается один раз — защита
   от циклов. Гонки с `pnpm install` (сам `readdirSync` увидел запись, а
   `realpathSync` её уже не находит, потому что pnpm в этот момент
   перелинковывает `node_modules/@packages` целиком) — не роняют процесс:
   ловятся только ожидаемые коды `ENOENT`/`ENOTDIR`, цикл помечается
   невалидным, попытка повторится на следующем файловом событии. Любая другая
   ошибка (не гонка, а баг) пробрасывается дальше и роняет процесс — это
   осознанно, чтобы не маскировать реальные поломки под "просто гонка".
2. **Структурная проверка.** `.env` без `env.ts` рядом — жёсткая ошибка
   (список таких директорий выводится разом, цикл невалиден).
3. **Проверка коллизий.** Одно и то же имя переменной, объявленное в `.env`
   двух разных пакетов/app'а — ошибка, никакого авто-namespace.
4. **Инжект в `process.env`.** Приоритет: значение, уже стоящее в
   `process.env` до нашего вмешательства (реальный OS/Docker env), никогда не
   перезаписывается. Значение из `.env`, однажды заинжектированное нами —
   при следующем цикле (в `--watch`) перезаписывается свежим содержимым
   файла безусловно (мы точно знаем, что именно поменялось). Переменная,
   которую мы раньше заинжектили, но она пропала из всех `.env` (файл
   удалили/переменную вычеркнули) — удаляется из `process.env`, а не
   остаётся призраком прошлого цикла.
5. **Валидация схемой.** Для каждого найденного `env.ts` — кэш `tsx`-модуля
   явно сбрасывается (`tsxRequire.resolve()` + `delete tsxRequire.cache[...]`,
   официальный API `tsx/cjs/api`, а не ручной перебор внутреннего формата
   ключа) перед повторным `require`, иначе долгоживущий `--watch`-процесс
   вернёт закэшированную версию модуля вместо актуального содержимого файла.
   Схема (`z.object`, спрятанная за `ENV_SCHEMA`-символом) валидируется через
   `safeParse(process.env)`; ошибка форматируется `z.prettifyError`.
6. **`--debug`.** Если всё провалидировалось — печатает итоговые значения по
   каждому пакету/app: без `console.table` (у него всегда есть неубираемая
   колонка `(index)`) и без повторяющейся колонки `package` — имя пакета
   заголовком, дальше `KEY = value`.

### Обычный запуск (без `--watch`)

Один `runCycle()`; если невалиден — `process.exit(1)` без запуска команды.
Если валиден — команда запускается через `crossSpawn.sync(cmd, args, { stdio:
'inherit', env: process.env })` (`cross-spawn`, не голый `node:child_process`
и без `shell: true` — сам резолвит `.cmd`/`.bat`-обёртки на Windows и
правильно экранирует аргументы), и код завершения workspace-env пробрасывает
код завершения команды:

- `result.error` (сам процесс не смог стартовать) — печатается явно, а не
  молча превращается в голый `exit 1`;
- `status === null` (процесс убит сигналом) — код завершения `1`, а не
  наивный `?? 0`, который выдал бы "успех" там, где процесс на самом деле
  убили.

### `--watch`

После первого успешного `runCycle()` поднимает дочернюю команду
(`crossSpawn(cmd, args, { stdio: 'inherit', env: process.env })`) и следит через `chokidar`
(`awaitWriteFinish` вместо самодельного debounce) за двумя видами директорий,
обе — `depth: 0` (только непосредственное содержимое, без рекурсии):

- **`packageDirs`** — app root и директория каждого найденного пакета,
  **включая те, у которых сейчас нет ни `.env`, ни `env.ts`**. Ловим
  появление, правку и удаление файла с именем `.env` или `env.ts`
  непосредственно внутри. Следим именно за директориями, а не за самими
  файлами: путь, которого ещё нет на диске, отслеживать нечем — если
  `.env`/`env.ts` появится позже, во время работающей сессии, это тоже будет
  замечено.
- **`scopeDirs`** — `node_modules/@packages` у app'а и у каждого пакета.
  Ловим появление/исчезновение **любой** записи — это `pnpm add`/`pnpm
  remove` зависимости во время работающего `--watch`: набор `.env`/`env.ts`
  пересобирается автоматически, без ручного перезапуска.

При срабатывании — сначала **валидирует новый цикл**, не трогая текущий
дочерний процесс: если он невалиден, старый (последний рабочий) процесс
продолжает жить как ни в чём не бывало — опечатка в `.env`/`env.ts` не должна
убивать рабочую сессию. Только если новый цикл валиден — убивает старый
дочерний процесс (`tree-kill`, не `child.kill()`: сам `nest start --watch`/
`vite` порождают своих детей вроде webpack — обычный `kill()` убивает только
непосредственного ребёнка, оставляя внуков-сирот висеть) и поднимает новый
со свежими значениями.

Если правка приходит, пока предыдущий рестарт ещё не завершился (например,
сразу два файла поменялись почти одновременно) — событие не теряется, а
откладывается и обрабатывается сразу после текущего цикла (`pendingRestart`).

При `SIGINT`/`SIGTERM` — дожидается реального завершения дерева дочернего
процесса (колбэк `tree-kill`, а не факт отправки сигнала) перед своим
собственным `process.exit()`: `tree-kill` на Windows асинхронный (отдельный
`taskkill`-процесс), и выход раньше его завершения оставляет осиротевшие
процессы висеть.

Это единственное место в проекте, реагирующее на изменение `.env`/`env.ts` —
в `webpack.config.js` намеренно нет отдельного watcher'а на те же файлы: два
независимых триггера рестарта одного и того же процесса на одно и то же
событие — гонка.

## Использование

```json
{
  "scripts": {
    "dev": "workspace-env --debug --watch --set NODE_ENV=development nest start --watch",
    "start": "workspace-env --set NODE_ENV=production node dist/main.js"
  }
}
```

Флаги — `--debug`, `--watch`, `--set` — принимаются только в самом начале, до
команды, иначе не отличить от одноимённых флагов дочерней команды.

- `--debug` — см. «`--debug`» выше.
- `--watch` — см. «`--watch`» выше.
- `--set KEY=value` (повторяемый) — разовый ad-hoc оверрайд `process.env` для
  этого запуска, в духе `cross-env` (кросс-платформенно — на Windows `KEY=value
  command` не нативный shell-синтаксис). Ничем не валидируется, просто
  пробрасывается как есть — принципиально отдельно от `.env`/`env.ts`
  (декларативных, закоммиченных, провалидированных схемой). Применяется до
  первой валидации, так что видно и самой схеме `env.ts`.

Пока идёт сам `pnpm add`/`remove`, `node_modules/@packages` может на
мгновение оказаться в противоречивом состоянии (pnpm перелинковывает разом
все записи, не только изменившуюся) — такой цикл просто помечается
невалидным и повторяется на следующем файловом событии, без падения
супервизора.
